---
title: "处理错误与恢复"
description: "区分未提交、结果未知与已受理，避免超时后重复发起业务操作。"
---

调用报错时，先确认请求是否已被服务端受理，再决定下一步。网络超时只表示本地没有按时拿到结果，不代表服务端没有执行。

| 遇到的情况 | 应用怎么处理 |
|---|---|
| 参数错误，且明确在发送前被本地校验拒绝 | 修正参数后重新发起 |
| 身份或权限错误 | 核对当前账号、票据和目标资源授权 |
| 数据未就绪、过期或仅部分覆盖 | 继续同步或重新观察，不能把缺失数据当作不存在 |
| 写入后超时、断线或结果未知 | 保留原 mutationId / clientCommandId，先查询原结果 |
| 版本冲突 | 读取最新状态，再由应用决定是否继续修改 |

## 已经拿到受理结果

保留返回的真实消息和 Turn 身份，继续查询或观察原任务。收到消息不等于任务完成；执行结束后还应核对最终展示是否完整。审批和问答也不能因页面超时而自动重复提交。

## 尚不能确认是否受理

支持 MutationOptions 的方法使用[写入结果跟踪](/domain-model/mutation)；消息命令使用[原命令回执](/domain-model/command-receipt)。不要换一个新 ID 重新提交相同业务意图，也不要把 retryable=true 直接理解为允许重试写入。

普通错误对象的 not_started 可能只是默认值。只有明确的写前拒绝或服务端未受理证据，才能据此判断没有产生副作用。

## 停止本地等待与取消远端任务

退出页面、退订、超时或关闭 Client 可以结束本地等待，但不证明远端任务已取消。需要取消时使用对应的公开取消接口，并继续核对任务终态。

排查身份、运行环境、升级和最小诊断信息见[错误与运维](/integration/04-errors-and-operations)与[排障](/support/troubleshooting)。不要通过删除本地数据库掩盖未确认的写入结果。
